# Operations Runbook

Practical guide for developing, building, testing, and deploying Open Mercato.

## Development

### Monorepo Setup (First Time)

```bash
# Prerequisites: Node.js 24, Git, Docker Desktop (PostgreSQL + Redis + Meilisearch)
corepack enable && corepack prepare yarn@4.12.0 --activate
git clone https://github.com/open-mercato/open-mercato.git
cd open-mercato && git checkout develop
docker compose up -d                  # starts PostgreSQL, Redis, Meilisearch
cp apps/mercato/.env.example apps/mercato/.env
# Set DATABASE_URL / JWT_SECRET / REDIS_URL in apps/mercato/.env
yarn dev:greenfield                   # installs, builds, seeds, starts the app
```

Open **http://localhost:3000/backend** — credentials printed in terminal.

### Daily Development

```bash
yarn dev                    # start dev server with package watching
yarn dev --watch=auto-optimized  # narrow watch scope for lower memory usage
yarn generate               # regenerate registries after module file changes
yarn typecheck              # type-check before committing
yarn lint                   # lint before committing
yarn test                   # run unit tests
```

### Dev Modes

| Flag | Effect |
|------|--------|
| `yarn dev` | Default: Turbopack, watches all packages |
| `yarn dev:classic` | Webpack instead of Turbopack |
| `yarn dev --watch=auto-optimized` | Watch only git-touched packages (lower memory) |
| `yarn dev --watch=popular` | Watch most frequently changed packages (default cap: 6) |
| `yarn dev:app` / `--app-only` | Watch only the app, not packages |
| `yarn dev:greenfield` | Fresh DB + seed + start |

Watch scope env vars: `OM_WATCH_SCOPE=all|auto-optimized|env|popular`, `OM_WATCH_PACKAGES=core,ui`

### Multiple Local Instances

```bash
# Explicit database name
yarn dev:greenfield --database-name=my_db
# Derive database name from current directory
yarn dev --database-name
# Standalone app
yarn setup --database-name=client_a
```

## Build Pipeline

The build follows a strict order (from `package.json` scripts and `.ai/agentic.config.json`):

```
build:packages → generate → build:packages → i18n:check-sync →
i18n:check-usage → typecheck → test → build:app
```

1. **`yarn build:packages`** — Turbo builds all `packages/*` workspaces (outputs `dist/`)
2. **`yarn generate`** — AST-based code generator scans modules and emits ~20 registry files under `apps/mercato/.mercato/generated/`
3. **`yarn build:packages`** (again) — rebuild after generated files exist
4. **`yarn build:app`** — builds the Next.js app (`@open-mercato/app`)

**Generated files:**
- **Ephemeral** (gitignored): `apps/mercato/.mercato/generated/`, `packages/*/generated/`, `src/generated/` — wiped by `yarn clean-generated`, regenerated by `yarn generate`
- **Versioned** (committed): `*.generated.ts` next to source (e.g., `apps/mercato/src/official-modules.generated.ts`) — survive `yarn clean-generated`, encode source-of-truth state

Never edit generated files by hand.

### Clean

```bash
yarn clean:generated    # remove ephemeral generated files
yarn clean:packages     # remove package dist/ folders
yarn clean              # both
```

## Database

### Migrations (MikroORM v7)

```bash
yarn db:generate       # generate migrations from entity changes
yarn db:migrate        # apply pending migrations
yarn db:greenfield     # drop + recreate + migrate + seed
yarn initialize        # run tenant initialization (setup.ts hooks)
yarn seed:defaults      # seed default data
```

Migrations are per-module. There is no global schema — each module owns its entities and migrations under `data/migrations/`.

**Ask before applying database migrations locally with `yarn db:migrate`;** normal PRs should include migration files and snapshots.

### Connection Budget

The DB connection budget invariant:

```
web_pool_max + worker_pool_max + scheduler/overhead ≤ Postgres max_connections
```

- `DB_POOL_MAX` (default 20) controls each process's pool
- Give workers a **smaller** `DB_POOL_MAX` than the web process
- `worker --all` fits `Σconcurrency` to the worker's connection budget at startup
- Override: `OM_WORKERS_DB_CONNECTION_BUDGET`

## i18n

Four locales: `en`, `de`, `es`, `pl`. Locale dictionaries live in each module's `i18n/` directory.

```bash
yarn i18n:check-sync    # validate all locales have the same keys
yarn i18n:check-usage   # detect unused/hardcoded translation keys
```

- User-facing strings go through `useT()` (client) or `resolveTranslations()` (server)
- Never hard-code user-facing strings or design-system status colors
- Translatable fields declared in module's `translations.ts`
- Run `yarn generate` after adding `translations.ts`

## Official Modules

Official modules live in a **git submodule** at `external/official-modules/` (not committed by default).

```bash
yarn official-modules                    # inspect/change activation
yarn official-modules add <module-name>  # add a module (runs git submodule add)
```

- Activation driven by `official-modules.json` (committed: `activated` is team default, `available` auto-filled when submodule present)
- `official-modules.local.json` — gitignored personal override
- Postinstall worker (`scripts/official-modules-setup.mjs`) regenerates `apps/mercato/src/official-modules.generated.ts`
- Module-id convention: package `@open-mercato/<suffix>` ⇒ module id `<suffix>` with dashes → underscores
- After activating/deactivating: `yarn mercato configs cache structural --all-tenants` (and `yarn dev:reset` if Turbopack serves stale chunk)
- Edits under `external/official-modules/` commit to the submodule's git, not open-mercato's

### Traefik Overlay (Custom Domains)

The base compose files do not include a reverse proxy. The opt-in Traefik overlay (`docker-compose.fullapp.traefik.yml`) terminates TLS for the platform domain and any verified custom hostname, gating certificate issuance through the app's `domain-check` endpoint via ForwardAuth. Use it when you need per-organization custom domains (portal or backend):

```bash
docker compose -f docker-compose.fullapp.yml -f docker-compose.fullapp.traefik.yml up -d
```

For dev, layer the dev overlay so ACME defaults to Let's Encrypt staging:

```bash
docker compose -f docker-compose.fullapp.dev.yml \
  -f docker-compose.fullapp.traefik.yml \
  -f docker-compose.fullapp.traefik.dev.yml up --build
```

Required Traefik env vars: `ACME_EMAIL`, `DOMAIN_CHECK_SECRET`, `DOMAIN_RESOLVE_SECRET`, `PLATFORM_PRIMARY_HOST`. See [`docker/traefik/README.md`](../../docker/traefik/README.md) for the full request flow and when to use the bundled Traefik vs an external proxy.

### Per-Organization Backend Domains

Supported on self-hosted Docker Compose with the Traefik overlay only (Railway registers one domain per service; AWS defers custom-domain ingress). The feature is off by default and **refuses to start** when enabled without a trusted-proxy declaration.

Each organization can bind its own hostname for the admin panel — `crm.staffinit.com` → organization "Staffinit" — on the same instance. This extends the existing portal custom-domain `DomainMapping` subsystem with a `target: 'portal' | 'backend'` discriminator rather than building a parallel one. On a bound host the hostname — not the organization switcher — determines which organization an operator acts on: a stale `om_selected_org` cookie is discarded, and a foreign-tenant session is refused with 403.

Setup steps (full guide: [`apps/docs/docs/deployment/backend-custom-domains.mdx`](../../apps/docs/docs/deployment/backend-custom-domains.mdx)):

1. `yarn db:migrate` — adds the `target` column to `domain_mappings`
2. Set `BACKEND_CUSTOM_DOMAINS_ENABLED=true` and `TRUSTED_PROXY_CIDRS` (and list the host in `APP_ALLOWED_ORIGINS` so email links follow it)
3. Start the Traefik overlay — no Traefik-side change is needed for backend domains
4. Grant `customer_accounts.domain.manage_backend` and run `yarn mercato auth sync-role-acls`
5. Register the domain at `/backend/customer_accounts/settings/domain`, choosing "Admin panel (backend)" as the target
6. Point DNS (CNAME to `CUSTOM_DOMAIN_CNAME_TARGET`) and verify — only an `active` mapping binds the organization

**One active backend domain per organization** (DB-enforced). Passkeys and sessions are per domain (host-only cookies). See [architecture/overview.md → Host Binding Org-Scope Clamp](../architecture/overview.md#host-binding-org-scope-clamp) for the authorization mechanism.

## Releases

- `main` — release-ready code, tagged and deployable
- `develop` — nightly builds and upcoming release work

### Runner Selection

If `DOCKER_COMPOSE_FILE` is set, use Docker mode. Otherwise probe (in order): `docker-compose.*dev*.local.yml` (sorted), `docker-compose.fullapp.dev.yml`, `docker-compose.fullapp.yml` — first file with a running `app` container wins → Docker mode; none → local mode (`yarn …` on host).

In Docker mode: `node scripts/docker-exec.mjs <cmd>` instead of `yarn <cmd>`.

## Backward Compatibility

Read `BACKWARD_COMPATIBILITY.md` before modifying any contract surface. It enumerates 13 contract-surface categories:

1. Auto-discovery files
2. Types
3. Signatures
4. Import paths
5. Event IDs
6. Widget spot IDs
7. API routes
8. DB schema
9. DI keys
10. ACL features
11. Notification IDs
12. CLI commands
13. Generated files

Each classified as FROZEN / STABLE / ADDITIVE-ONLY. Breaking changes block merge unless the deprecation protocol is followed: (1) never remove in one release, (2) add `@deprecated` JSDoc, (3) provide a bridge for ≥1 minor version, (4) document in `UPGRADE_NOTES.md`, (5) reference a spec with migration section.

## Security

- Never expose cross-tenant data or skip tenant/organization scoping
- Never commit credentials, tokens, private keys, or local-only ops files
- Use `findWithDecryption()` / `findOneWithDecryption()` for encrypted entities
- AI Code Mode enforces tenant/org scope on `api.request()` calls
- Attachments enforce scope invariant (no partial-null tenant/org pairs)
- Webhooks use Standard Webhooks signing
- Workflows SSRF-guard `CALL_WEBHOOK` activities
- See `SECURITY.md` for security practices
