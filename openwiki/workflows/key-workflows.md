# Key Workflows

This page covers the major runtime and development workflows in Open Mercato — how requests flow through the system, how data mutations work, how events propagate, and how cross-module features connect.

## Request Lifecycle

Every HTTP request passes through the Next.js App Router catch-all dispatchers, which enforce auth, tenancy, and RBAC before reaching the handler:

```
Client request
  → Next.js catch-all dispatcher (api / backend / frontend)
    → Route manifest matching (specificity-sorted patterns)
      → Auth middleware (JWT session validation)
        → Tenant selection (enforceTenantSelection — superadmins can cross-tenant)
          → Organization scope resolution (cookie + RBAC + cache)
            → RBAC feature check (wildcard-aware matchFeature)
              → Rate limiter
                → DI container (per-request Awilix)
                  → Handler execution (route handler / page component / subscriber)
                    → Response (enriched, optimistic-lock headers)
```

**Key dispatchers:**
- API: `apps/mercato/src/app/api/[...slug]/route.ts`
- Backend admin: `apps/mercato/src/app/(backend)/backend/[...slug]/page.tsx`
- Frontend: `apps/mercato/src/app/(frontend)/[...slug]/page.tsx`

## CRUD Route Factory (`makeCrudRoute`)

Most CRUD APIs are generated by `makeCrudRoute()` from `@open-mercato/shared/lib/crud/factory.ts`. It handles the full lifecycle:

1. **Zod validation** — request body validated against `data/validators.ts` schemas
2. **RBAC feature gating** — `requiredFeatures` checked via wildcard-aware `matchFeature()`
3. **CRUD operations** — list (with pagination, filtering, multi-ID `?ids=`), detail, create, update, delete
4. **Custom fields** — `collectCustomFieldValues()` on write, `normalizeCustomFieldResponse()` on read
5. **Optimistic locking** — `updated_at` column checked on update/delete (default ON, `OM_OPTIMISTIC_LOCK=off` to disable)
6. **Response enrichers** — cross-module response augmentation via `data/enrichers.ts`
7. **API interceptors** — `api/interceptors.ts` before/after hooks, body/query rewriting
8. **Mutation guards** — command-pattern side effects fire after commit
9. **CRUD list caching** — cache with tag-based invalidation, invalidated post-commit
10. **Sync event emission** — `emitCrudSideEffects()` dispatches indexing/search/cache events

Reference: `packages/core/src/modules/customers/` (reference CRUD module).

## Command Pattern (Write Operations)

Write operations MUST go through the Command pattern, not direct ORM writes in route handlers. The `customers` module is the reference implementation.

**Why:** Commands provide transactional safety, undo support, custom field snapshots, and post-commit side-effect dispatch.

**Pattern:**
```typescript
// packages/core/src/modules/customers/commands/people.ts
export async function createPerson(ctx, input) {
  return withAtomicFlush(em, [
    // Phase 1: scalar + relation mutations (inside transaction)
    async () => { /* create entity, set relations */ },
    // Phase 2: side effects (after commit)
    async () => {
      await eventBus.emit('customers.person.created', { ... }, { trustedScope })
      await cacheService.invalidateTag('customers')
    },
  ], { transaction: true })
}
```

**Key rules:**
- Never interleave `em.find()`/`em.findOne()` between a scalar mutation and `em.flush()` — use `withAtomicFlush` phases
- Side effects (cache invalidation, event emission, search indexing) fire **after commit**, never inside the transaction
- Custom field snapshots captured in `before`/`after` payloads for undo support
- `buildCustomFieldResetMap(before.custom, after.custom)` for undo operations

**Sales document commands:** Sub-resources (lines, adjustments, shipments, payments, returns) guard against the **parent order's** `updated_at`, not their own, because they recalculate order totals. The order is the consistency boundary. See `packages/core/src/modules/sales/commands/shared.ts` → `enforceSalesDocumentOptimisticLock`.

## Optimistic Locking

Default ON for every `makeCrudRoute` entity. Prevents silent lost updates on concurrent edits.

- **Entity requirement:** `updated_at` column on every user-editable entity
- **API contract:** List/detail responses return `updatedAt`; mutating requests send `If-Match` header via `buildOptimisticLockHeader(record.updatedAt)`
- **Conflict response:** 409 with structured body; client surfaces via `surfaceRecordConflict(err, t)` or the unified conflict bar
- **Command-pattern writes:** Use `enforceCommandOptimisticLock` (document aggregate) or `createCommandOptimisticLockGuardService` (enterprise seam)
- **Opt out:** `OM_OPTIMISTIC_LOCK=off` (kill switch)
- **Enforcement tests:** `optimistic-lock-editable-entities.test.ts`, `optimistic-lock-ui-coverage.test.ts`

Reference: `packages/shared/src/lib/crud/optimistic-lock.ts`, `packages/shared/src/lib/crud/optimistic-lock-command.ts`

## Event Bus

Modules communicate via typed events. Never use direct module-to-module function calls for side effects.

### Event Declaration
```typescript
// src/modules/<module>/events.ts
import { createModuleEvents } from '@open-mercato/shared/modules/events'
const events = [
  { id: 'customers.person.created', label: 'Person Created', entity: 'person', category: 'crud' },
  { id: 'customers.deal.won', label: 'Deal Won', entity: 'deal', category: 'lifecycle' },
] as const
export const eventsConfig = createModuleEvents({ moduleId: 'customers', events })
```

### Event Categories
- **crud** — entity create/update/delete lifecycle
- **lifecycle** — domain events (e.g., `customers.deal.won`, `sales.document.totals.calculated`)
- `excludeFromTriggers: true` — prevents workflow trigger storms (used on `*.calculate.before/after`, `*.pricing.resolve.before/after`)
- `clientBroadcast: true` — bridges to browser via SSE (DOM Event Bridge) for DataTable refresh
- `portalBroadcast: true` — bridges to customer portal via SSE

### Subscription Types
| Type | Persistence | Retry | Use case |
|------|------------|-------|----------|
| Ephemeral | In-memory only | No | Real-time UI updates, cache invalidation |
| Persistent | Stored in queue | Yes | Notifications, indexing, audit logging |

### Delivery
- `QUEUE_STRATEGY=local` → persistent events process from `.mercato/queue/`
- `QUEUE_STRATEGY=async` → persistent events dispatch through BullMQ (Redis)
- `OM_EVENTS_SINGLE_DELIVERY` (default ON) — single-delivery semantics for persistent events
- Ephemeral subscribers always run in-process

### Trusted Scope
Trusted tenant/org scope comes from `emit(..., options)` or queued job options — **never from payload fields**. This prevents cross-tenant data leakage through fabricated payloads.

## Search Indexing

Three strategies, each with different backends:

| Strategy | Backend | When to use |
|----------|---------|-------------|
| Fulltext | Meilisearch (`MEILISEARCH_HOST`) | Fast, typo-tolerant search (names, descriptions) |
| Vector | Embedding provider (OpenAI or Ollama) | Semantic/meaning-based search |
| Tokens | PostgreSQL (always available) | Baseline keyword search without external services |

### Configuration
Each module with searchable entities declares a `search.ts`:
- `fieldPolicy.excluded` — sensitive fields never indexed (passwords, tokens, SSNs)
- `fieldPolicy.hashOnly` — PII fields (email, phone, tax_id) — exact-match only, no fuzzy
- `buildSource` — constructs the text/embedding source; MUST include `checksumSource`
- `formatResult` — formats token search results (without it, users see raw UUIDs)
- Entity IDs use `module:entity_name` format

### Indexing Flow
1. CRUD side effects (`emitCrudSideEffects`) fire post-commit
2. Search indexer receives events via subscribers
3. Entities re-indexed (fulltext → Meilisearch, vector → pgvector, tokens → PostgreSQL)
4. `checksumSource` detects unchanged entities → skips redundant re-embedding

### Provider Probe
- Ollama checked via `GET {OLLAMA_BASE_URL}/api/tags` (not assumed reachable)
- Key-based providers checked via env-key presence
- Cached, fail-closed probe — embeddings POST rejects unreachable providers with `409`
- Ollama URL safety enforced: `packages/search/src/vector/lib/ollama-url-safety.ts`

### Tenant-Scoped Settings
Search settings (Cmd+K strategies, embedding provider/model, auto-index flag) are tenant-scoped. A tenant with no saved row inherits instance default, then env-derived default. GET responses carry `source: tenant | instance | env`.

## Workflow Engine

Business process automation via `packages/core/src/modules/workflows/`. Step-based workflows with visual editor (React Flow).

### Execution Architecture
```
Definition → startWorkflow() → Instance → executeWorkflow() loop
  → stepHandler.enterStep()
    → USER_TASK (pause) | AUTOMATED (transition) | WAIT_FOR_* (pause) | END (complete)
      → transitionHandler.executeTransition()
        → activityExecutor (sync or async)
          → next step...
```

### Step Types
`START`, `END`, `USER_TASK`, `AUTOMATED`, `SUB_WORKFLOW`, `WAIT_FOR_SIGNAL`, `WAIT_FOR_TIMER`, `PARALLEL_FORK`, `PARALLEL_JOIN`

### Activity Types
`SEND_EMAIL`, `CALL_API`, `CALL_WEBHOOK` (SSRF-guarded), `UPDATE_ENTITY`, `EMIT_EVENT`, `EXECUTE_FUNCTION`, `WAIT`

### Key Rules
- **Event sourcing:** All state changes logged via `eventLogger.logWorkflowEvent()`
- **Idempotent handlers:** Activities may be retried; handlers check state before mutating
- **Variable interpolation:** `{{context.*}}`, `{{workflow.*}}`, allowlisted `{{env.*}}`, `{{now}}` — secrets never interpolated
- **SSRF guard:** `CALL_WEBHOOK` uses `redirect: 'manual'` (3xx rejected), private URL blocking via `@open-mercato/shared/lib/url-safety`
- **Trigger storms:** `debounceMs` and `maxConcurrentInstances` prevent runaway creation
- **Compensation:** Saga pattern — on failure, compensation activities execute in reverse order

### Cross-Module Integration
- Event triggers: wildcard subscriber evaluates all non-internal events (excluded prefixes: `query_index`, `search`, `workflows`, `cache`, `queue`)
- Business rules: workflow transitions reference rule IDs from `business_rules` module as `preConditions`
- Example: `sales.order-approval` workflow triggered by `sales.orders.created`

## AI Mutation Approval

AI-driven data mutations MUST go through `prepareMutation(...)` + pending-action approval. The runtime fails closed if the approval contract is bypassed.

**Flow:**
1. AI tool handler calls `prepareMutation(...)` with a preview of the intended change
2. User sees an approval card with before/after diff
3. On approval, the mutation executes via the command pattern
4. On rejection, the mutation is discarded

**Rules:**
- `isMutation: true` on write tools — policy gate strips these from read-only agents
- `mutationPolicy`: `'read-only'` | `'confirm-required'` | `'destructive-confirm-required'`
- Code Mode `api.request()` enforces endpoint-level RBAC + tenant/org scope before fetch (see `packages/ai-assistant/src/modules/ai_assistant/lib/scope-injection.ts`)

## Custom Fields / Dynamic Entities

The `entities` module provides an EAV (Entity-Attribute-Value) system for custom/dynamic fields on any entity.

### Integration Pattern
1. Modules register virtual entities via `upsertCustomEntity(em, 'module:entity', { label, description })`
2. Modules ship default custom fields via `ce.ts` → `entities[].fields` → `yarn mercato entities install`
3. `CrudForm` auto-appends custom fields when `entityId` is passed
4. CRUD operations wire `collectCustomFieldValues()` for writes
5. Detail/read APIs normalize response keys via `normalizeCustomFieldResponse()` (bare field names, not `cf_` prefixed)
6. Query layer supports `cf:<key>` selectors for filtering/projection

### Field Kinds
`text`, `multiline`, `integer`, `float`, `boolean`, `select`, `currency`, `relation`

### Admin UI
Backend → Data designer → System/User Entities. Code-defined entities cannot be deleted from UI; only custom (virtual) entities can.

## Widget Injection

Cross-module UI extension via declarative widget injection.

### Spot ID Conventions
- `data-table:<entity>:<slot>` — DataTable extensions (columns, row actions, bulk actions, filters)
- `detail:<entity>:<slot>` — detail page extensions
- `crud-form:<entity>:<slot>` — form field injections
- `page:*` — page-level overrides

### Pattern
1. Module declares widgets in `widgets/injection/` (server `widget.ts` + client `widget.client.tsx`)
2. Widget-to-slot mappings in `widgets/injection-table.ts`
3. `yarn generate` registers widgets in the manifest
4. Host module renders widgets at declared spots

### Component Replacement
Use `widgets/components.ts` for replacing/wrapping UI components via `replace`/`wrapper`/`props` with handle-based IDs.

## Cache Invalidation

Cache invalidation and query-index side effects fire **after** the originating domain write commits.

- Cache entries tagged with entity type + tenant
- `invalidateTag('customers')` clears all customer-related cache
- Post-commit dispatch prevents stale reads within transactions
- `OM_CACHE_SAFETY_ALWAYS_CONSISTENT` (planned, default OFF) — would make read-projection tail converge synchronously

Reference: `packages/cache/AGENTS.md`, `.ai/specs/2026-06-05-cache-safety-always-consistent.md`

## Background Workers

Workers process queued jobs (events, webhooks, search indexing, scheduled tasks).

### Worker Contract
```typescript
export const metadata = { queue: 'my-queue', id: 'my-worker', concurrency: 5 }
export default async function handler(job) { /* ... */ }
```

### Rules
- MUST be idempotent — jobs may be retried
- MUST test with both `QUEUE_STRATEGY=local` and `QUEUE_STRATEGY=async`
- Concurrency capped at 20
- DB connection budget: `web_pool_max + worker_pool_max ≤ Postgres max_connections`
- Workers that call external services MUST bound calls with a timeout

### Running Workers
```bash
yarn mercato <module> worker <queue-name> --concurrency=5
```
