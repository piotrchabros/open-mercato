# Per-organization backend domains

Give each organization its own hostname for the **admin panel** — `crm.bespokesoft.pl`,
`crm.staffinit.com`, `crm.bluebee.marketing` — all served by one instance. Operators sign in on
their own branded domain and land directly in that organization.

This extends the customer-portal custom-domain subsystem rather than duplicating it, so DNS
verification, on-demand TLS and the admin UI are the ones you already know.

:::warning Supported on self-hosted Docker Compose with the Traefik overlay only
Railway registers a single domain per service, and the AWS playbook defers custom-domain ingress.
The feature is off by default and **refuses to start** when enabled without a trusted-proxy
declaration.
:::

## What the hostname actually decides

Not just branding. On a bound host the hostname — not the organization switcher — determines which
organization an operator acts on:

- A stale `om_selected_org` cookie pointing at another organization is **discarded**. The hostname
  wins.
- A session belonging to a **different tenant** is refused with 403. Serving it the host's
  organization would hand over data it has no claim to.
- The organization switcher renders as a fixed indicator instead of a picker, and the
  "all organizations" option disappears.

The hostname can only ever *narrow* what a session already grants. It never grants access: a
user without permission on the bound organization gets an empty scope, not a fallback to their own.

## Working across several organizations

A bound hostname serves exactly one organization. That raises an obvious question, and the answer
is that **the platform domain is untouched and remains the multi-organization workspace**.

The clamp only engages when a request arrives on a bound hostname. On the platform host there is
no binding, so the organization switcher, the "all organizations" option and every cross-organization
view behave exactly as they did before this feature existed.

| You want to | Do this |
|---|---|
| Switch freely between organizations as a super-admin | Work on the platform domain — the host named in `PLATFORM_DOMAINS`. Nothing changed there. |
| See a parent organization and its children at once | Bind the **parent's** domain. The scope is the bound organization *plus its descendants*, so the whole subtree is visible. |
| See two unrelated organizations side by side | Use the platform domain. A bound host cannot show an organization outside its own subtree — that is the guarantee it exists to provide. |
| Brand only some organizations | Nothing to do. The feature is opt-in per organization: one without a mapping is simply reachable via the platform host only. |

### Does switching organizations mean signing in again?

Only if you change hostname. The two look similar from a chair and are not the same thing.

| Action | Re-authentication |
|---|---|
| Picking another organization in the switcher, on the same host | **No.** It writes the `om_selected_org` cookie and refreshes the page. Same session throughout. |
| Opening a different branded domain | **Yes.** Session cookies carry no `Domain` attribute, so they are host-only: the session on `crm.acme.com` is never sent to `crm.staffinit.com`. |

The platform domain is no exception — signing in there does not sign you in on a branded host, and
the reverse is equally true. This holds even when the hostnames share a parent domain, because
host-only means precisely that host.

This is pre-existing behaviour, not something per-organization domains introduced. It only starts
to matter once there is more than one backend hostname to move between.

The practical consequence: an operator covering all three organizations belongs on the platform
domain, where switching is one click. Branded domains suit people tied to a single organization —
a Staffinit employee signs in once on `crm.staffinit.com` and never moves.

:::note One sign-in across every branded domain is cross-domain SSO
Deliberately out of scope, here and in the portal custom-domain work it builds on. It needs a
central identity provider and a redirect flow; no cookie setting can produce it.
:::

A user whose permissions cover several organizations still gets clamped to the bound one when they
arrive on a branded host — and if they have no permission on it at all, they get an empty scope
rather than a quiet fallback to an organization they *can* see.

## 1. Apply the migration

The `target` column on `domain_mappings` is what separates a portal domain from a backend one.

```bash
yarn db:migrate
```

## 2. Configure the environment

```bash
# Required
BACKEND_CUSTOM_DOMAINS_ENABLED=true
TRUSTED_PROXY_CIDRS=10.0.0.0/8

# The platform's own host(s) — comma-separated, hostname only
PLATFORM_DOMAINS=openmercato.example

# Where operators point their CNAME
CUSTOM_DOMAIN_CNAME_TARGET=portal.openmercato.example

# Secrets for the resolution + TLS-gate endpoints: openssl rand -hex 32
DOMAIN_CHECK_SECRET=…
DOMAIN_RESOLVE_SECRET=…
INTERNAL_APP_ORIGIN=http://127.0.0.1:3000

# So outbound email links follow the branded host — see the caveat below
APP_ALLOWED_ORIGINS=https://crm.bespokesoft.pl,https://crm.staffinit.com
```

`TRUSTED_PROXY_CIDRS` is not optional. The request `Host` header decides the organization, and it
is only trustworthy behind a proxy that overwrites it. The base compose file publishes the app
directly on its port, where any client can send whatever `Host` it likes — so the app refuses to
boot with the feature on and no proxy declared.

### `PLATFORM_DOMAINS` is an exclusion list

Two things about this variable are easy to get wrong, and neither fails in a way that points at
the cause.

**It is not derived from `APP_URL`.** They are separate settings. If `APP_URL` is
`https://panel.example.com` and `PLATFORM_DOMAINS` is left unset, it falls back to
`localhost,openmercato.com` — which does not contain your own host, so the proxy treats your admin
panel as a customer domain and performs a database lookup on **every page request**. (This is
exactly the bug the Railway deployer shipped: it set `APP_URL` and never `PLATFORM_DOMAINS`.)

**Do not list the organizations' hostnames there.** `PLATFORM_DOMAINS` names the hosts that must
*not* take part in per-organization routing. Adding `crm.acme.com` to it says "this is not an
organization domain", and two things follow:

- **The binding stops existing.** `resolveByHostname` returns `null` for a platform host, so no
  `hostBinding` is produced, the scope clamp never engages, and the hostname behaves like an
  ordinary admin panel with a full organization switcher — the opposite of what you configured it
  for.
- **The certificate is refused.** Traefik's `platform` router matches a single host
  (`PLATFORM_PRIMARY_HOST`) and bypasses the ACME gate. Every other hostname reaches the catch-all
  router, whose ForwardAuth asks `/api/customer_accounts/domain-check` — and that endpoint also
  returns "not eligible" for a platform host. The host ends up with no TLS at all.

So a three-organization instance wants a **fourth, neutral** hostname for administration:

```bash
PLATFORM_DOMAINS=panel.example.com
PLATFORM_PRIMARY_HOST=panel.example.com   # same host, for the Traefik router

# these stay OUT of the list, which is why they bind:
#   crm.acme.com          → Acme
#   crm.staffinit.com     → Staffinit
#   crm.bluebee.marketing → BlueBee
```

An operator who needs every organization signs in on `panel.example.com` and gets the full
switcher there. Nothing has to be added to `PLATFORM_DOMAINS` for that to work — it works
*because* that host is the only entry.

### Two variables that must stay unset

| Variable | Why the app refuses to start |
|---|---|
| `OM_SECURITY_WEBAUTHN_RP_ID` | Pinning the relying-party id to a shared parent domain so one passkey works everywhere makes **every** tenant host a valid relying party for **every** other tenant's passkey. Leave it unset; the id is derived per host and passkeys are enrolled per domain. |
| `OM_ALLOW_FORCED_HOST` | The test-only `x-force-host` override lets any caller holding `FORCE_HOST_SECRET` name an arbitrary hostname — which becomes an organization-selection bypass once the hostname decides scope. |

## 3. Start Traefik

The overlay is opt-in; the base compose file does not load it.

```bash
docker compose -f docker-compose.fullapp.yml -f docker-compose.fullapp.traefik.yml up -d
```

No Traefik-side change is needed for backend domains. Its catch-all router already matches any
hostname, and the ForwardAuth gate that authorises certificate issuance is target-agnostic — both
portal and backend hostnames are eligible.

## 4. Grant the permission

Registering a backend domain sits behind its own ACL feature, separate from the portal one:
it decides which organization operators act on, which is a higher privilege than pointing a
storefront at a hostname.

```
customer_accounts.domain.manage_backend
```

Grant it, then sync:

```bash
yarn mercato auth sync-role-acls
```

The domain settings page itself still requires `customer_accounts.domain.manage`.

## 5. Register the domain

Go to **`/backend/customer_accounts/settings/domain`**, pick the organization, and register the
hostname. Choose **“Admin panel (backend)”** in the target selector.

The selector only appears when the feature flag is on *and* you hold
`customer_accounts.domain.manage_backend`. If you cannot see it, one of those two is missing — both
are re-checked server-side, so the selector's absence is a symptom, not the cause.

## 6. Point DNS and verify

Create a CNAME from your hostname to whatever `CUSTOM_DOMAIN_CNAME_TARGET` holds, then run the
verification step in the panel. Verification is a real DNS lookup, not a TXT record.

The mapping moves `pending → verified → active`, and TLS is issued automatically. **Only an
`active` mapping binds the organization** — until then the hostname resolves to nothing and the
admin panel is not served there.

## Limits and consequences

**One active backend domain per organization.** Enforced by a database constraint. An organization
can still hold a second row while swapping domains with no downtime.

The per-organization cap of two domains is counted **per target**, so a portal domain and a backend
domain do not compete for the same slots.

**Passkeys are per domain.** A passkey registered on one hostname does not work on another — that
is how WebAuthn works, and the alternative is the cross-tenant hole described above. Users with a
passkey arriving on a new domain enrol a new one; recovery codes cover the gap.

**Sessions are per domain.** Cookies are host-only, so signing in on `crm.staffinit.com` does not
sign you in on the platform host — see [Does switching organizations mean signing in
again?](#does-switching-organizations-mean-signing-in-again) for how that differs from using the
switcher.

**Email links need the host in `APP_ALLOWED_ORIGINS`.** Request-scoped senders — password reset,
invitations, session refresh — resolve their base URL synchronously and read that static
allowlist, so a hostname registered through the panel keeps producing platform-host links until you
add it there and restart. The links work; they are just not branded. Queue and CLI senders resolve
from the database and need no such step.

## Verifying it works

```bash
# The platform host is unaffected
curl -I https://openmercato.example/backend

# The branded host serves the admin app, not the portal
curl -I https://crm.staffinit.com/backend

# A portal host refuses admin routes outright
curl -I https://shop.acme.com/backend   # 404
```

Signing in on `crm.staffinit.com` should land in the Staffinit organization with the switcher
showing it as fixed. If you still see a switcher with several organizations, the mapping is not
`active` yet.
